# 通信领域中文审稿（review-comm-cn）

## 任务概述

读取用户提供的 **PDF 论文**（及可选的 **此前审稿意见**），基于论文实际内容撰写 **中文通信/信息类学术审稿意见**。输出为连贯 prose，而非表格或打分卡；不给出录用/拒稿结论，除非用户明确要求。

**两种审稿模式**：

| 模式 | 触发条件 | 侧重点 |
|------|----------|--------|
| 初审 | 仅提供 PDF | 总结 + 优点 + 5–10 条新问题 |
| 复审/修回 | 提供 PDF + 此前审稿意见（及可选作者 response） | **先**概括修改成效与不足（主题式总结，非逐条），**再**提出仍存问题（**最多 5 条**） |

## 工作流程

### 1. 确认输入

1. **稿件 PDF**（必需）：确认路径（用户附件、工作区文件或指定路径）。
2. **此前审稿意见**（可选）：可为上一轮 `Review_*.md`、编辑部转来的审稿意见文本、或用户粘贴的条目。若提供，进入 **复审模式**。
3. **作者 response / 修改说明**（可选，复审时）：作者逐条回复信、Cover Letter 中的修改说明等。与修改稿、此前意见对照阅读。
4. 使用 **pdf** skill 提取稿件全文：优先 `pypdf` 或 `pdfplumber`；扫描件或提取质量差时尝试 OCR。

通读并记录：
- 标题、摘要、关键词
- 引言中的问题陈述与应用场景
- 方法/系统/算法设计与声称的贡献
- 实验设置、对比方法、指标与图表
- 结论与局限性；修改稿中常见的「修改说明」「回应审稿人」等段落

信息不足时，基于已有内容保守推断，**不编造**引用、数值、对比结果或未出现的实验。

### 2. 分析论文

按以下维度扫描全文，为「优点」和「问题」收集 **可追溯到论文事实** 的论据：

| 维度 | 关注内容 |
|------|----------|
| 场景与动机 | 面向何种网络/系统/应用；问题是否界定清楚 |
| 创新点 | 相对现有工作的技术增量；是否明确写出 |
| 方法设计 | 模块划分、算法流程、假设与复杂度 |
| 实验 | 数据集、基线、指标、消融、统计显著性 |
| 表达与排版 | 定义、符号、定理证明、图表清晰度 |

**复审模式额外步骤**：通读此前审稿意见（及作者 response），归纳上一轮主要关切 **主题**（如实验不足、场景契合、表述不清、图表缺失等）；再在修改稿中核对相应章节、实验、图表与文字变动，记录 **哪些主题已明显改进、哪些仅部分改进、哪些基本未触及**。这些认识用于撰写 **修改情况总结段**，输出时 **不做逐条编号回应**。

撰写前阅读 `references/example_review.md`（初审）与 `references/example_revision_review.md`（复审）把握语气与结构。

### 3. 撰写审稿意见

#### 3.1 输出结构（固定）

```markdown
# Review_[论文主题简短描述]

## 致编辑部（读者不可见）

[2–4 句宏观摘要：整体评价、主要贡献层级、核心优势与主要顾虑类型、处理建议倾向；不写具体问题编号与细节]

[开篇段落：2–4 句]
- 第一句：论文针对的应用/场景 + 提出的核心方案/方法；
- 随后：主要技术组合或创新机制（基于摘要与方法节事实）；
- 末句或穿插：1–2 条可核实的优点，语气客观、不夸大。

[复审模式：修改情况总结段，见 3.3]

[问题部分：见 3.2 / 3.4]
```

#### 3.2 初审模式 — 问题部分

```markdown
本文存在几点问题。

1、[问题 1]

2、[问题 2]

…

N、[问题 N]（共 5–10 条）
```

#### 3.3 复审模式 — 修改情况总结段

**紧接开篇段落之后**，用 **1 段连贯 prose**（约 80–180 字）概括修回成效，**不要**按上一轮意见逐条编号回应：

```markdown
相比上一版，修改稿在[主题 A，如实验验证/方案表述/相关 work]方面做了[更深入的分析/补充实验/新增图表等]，[可点出 1–2 处具体改动，如补充消融、新增流程图]，使得稿件在[完整性/可读性/说服力等]上有所提升；但在[主题 B]等方面，[仍显不足/改进有限/与作者 response 中的承诺尚有一定差距]。
```

写作要点：
- **主题归纳**：将上一轮多条意见按关切类型合并叙述（实验、场景建模、表达、图表等），而非「第 1 条…第 2 条…」。
- **结合事实**：依据修改稿正文变动、新增图表/实验，以及作者 response 中的说明；可肯定已改进之处，也可指出回应不充分之处，但保持 **段落式总结**。
- **语气**：客观、建设性；避免简单罗列「已回应/未回应」清单。
- **禁止**：复制上一轮审稿意见的编号结构；长段复述 response 原文。

#### 3.4 复审模式 — 问题部分

修改情况总结段之后，用与初审相同的过渡句引出 **仍存在的问题**：

```markdown
本文仍存在几点问题。

1、[仍存或新发现的问题；可涵盖上一轮已提出但未充分解决者，以及审阅修改稿后新注意到者；**共 1–5 条，不得超过 5 条**]

2、…
```

- 问题列表 **不必**与上一轮意见条数对应；按当前稿仍须改进之处组织即可，**优先保留最重要、最具决定性的意见**。
- **硬性上限**：复审模式下问题条数 **不得超过 5 条**；若候选意见较多，合并同类项或将在总结段已充分说明的次要问题删去。
- 已在总结段充分肯定的改进项，勿在问题列表中重复批评；若某主题仅部分改进，可在问题列表中用 **一条** 深化说明剩余缺口。

#### 3.5 致编辑部（读者不可见）

- **读者**：期刊编辑部；该节 **不** 进入作者可见的审稿意见正文（若系统只需一份文件，仍保留此标题，由用户自行拆分投递）。
- **内容**：宏观 summary，约 80–150 字。可含：
  - 工作所属方向与问题重要性（一句）
  - 创新性与完整性的整体判断（一句）
  - 主要风险类型（如实验验证不足、贡献表述过强等），**不展开具体第几条**
  - 倾向性建议（如「建议修改后再审」「整体可接受但需补强实验」），除非用户要求不给建议
- **禁止**：罗列具体问题编号、复述问题列表、与开篇段落逐句重复。

### 4. 问题来源（必须覆盖）

从下列 **六类** 中选取与论文最相关的类别生成问题列表；至少覆盖 **3 类**（复审模式下若仅列 3–5 条，仍须尽量覆盖 **2 类以上**），每条应能归入其中一类：

1. **表达不清晰** — 阶段目的不明、逻辑跳跃、符号/术语混用、定理或证明难读
2. **定义明显有问题** — 概念界定模糊、与领域惯例不符、符号前后不一致
3. **实际内容与声称的贡献存在冲突** — 摘要/引言承诺与正文或实验不一致；通用方法未体现场景特性
4. **实验设计不完整** — 缺基线、缺消融、数据集/场景单一、指标选取不当、未考虑实际约束
5. **结果分析不全面** — 缺曲线/可视化、缺误差分析、未讨论失败案例或复杂度/开销
6. **图表及排版混乱** — 缺流程图/算法图、图表信息不足、排版影响阅读

详细写作角度见 `references/weakness_categories.md`。

### 5. 输出与保存

- 默认在对话中直接给出完整审稿意见（含「致编辑部」节）。
- 用户要求保存时，写入工作区，文件名建议 `Review_<论文关键词>.md`。
- 不输出英文审稿，除非用户另行要求。

## 风格规则

- **语言**：简体中文，通信/信息类期刊审稿语气。
- **事实性**：每条意见应能在论文中找到依据或合理缺失点；不虚构他文对比或实验数据。
- **篇幅**：开篇 80–200 字；每条问题 1–3 句；致编辑部 80–150 字。初审问题 5–10 条；复审问题 **1–5 条**。
- **与 paper-reviewer 的区别**：本 skill 采用 **致编辑部摘要 + 单段总结 + 编号问题** 的通信审稿体例；复审时增加 **修改情况总结段**（主题式，非逐条回应）。

## 质量自检（输出前）

- [ ] 是否包含 `## 致编辑部（读者不可见）` 且内容为宏观摘要、无具体问题罗列？
- [ ] 开篇是否写明场景与创新点？是否至少 1 条基于事实的优点？
- [ ] 复审模式：是否在开篇后有一段 **主题式** 修改情况总结（非逐条编号回应）？
- [ ] 复审模式：总结段是否结合了此前意见、修改稿变动与（如有）作者 response？
- [ ] 初审：问题是否 5–10 条？复审：问题是否 **不超过 5 条**？
- [ ] 问题列表是否与总结段已充分肯定的改进不重复？
- [ ] 序号格式是否为 `N、`？初审新问题是否至少覆盖 3 类问题来源？复审是否至少覆盖 2 类？
- [ ] 是否存在无依据的批评或编造数据？
- [ ] 整体语气是否与 `references/example_review.md` 一致？
