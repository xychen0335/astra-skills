# 风格校准例

这些片段来自用户认可的技术博客及本次改稿经验。它们示范结构与语气，不作为新任务的技术事实来源，也不要求照抄句式。

## 从一个操作上的困难引出方法

参考《扩散模型的强化学习：如何把生成轨迹变成策略》：

> 对同一个 prompt 生成八张图，奖励模型很容易选出其中更好的几张。真正困难的是下一步：怎样把最终图片的一个分数，传回几十个去噪步骤从而完成策略模型的更新呢？

开头让读者先看到输入、输出与瓶颈，随后进入 Flow-GRPO 的 MDP、随机策略和更新机制。不要把它泛化成每篇文章都必须用问句开场。

这篇文章后续按技术依赖推进：Rectified Flow → MDP → ODE/SDE → 可计算的策略概率 → GRPO 更新。每段解释下一步为什么必要，公式用于完成推导。

## 工程内容落到生命周期和数据职责

参考《基于 AgentScope 的 AutoResearch 平台》：

> 每一轮用户消息进来，运行时做四件事：恢复状态、装配 Agent、消费 reply_stream、落库。

随后解释各步骤具体读写什么，并给出 Agent 装配代码。持久化部分比较数据库、工作区文件和事件总线的职责；Skills 部分说明索引、按需加载与工具组的关系。

值得复用的是“沿一次运行解释组件如何配合”，而不是原文特定的角色数、工具命名或权限方案。其他项目应按其真实实现组织文章。

## 本次获得认可的改稿方向

用户先否定了把选文理由、审查边界和个人评价放在前面的写法，随后认可了《Skill 自进化：如何把执行轨迹变成可复用经验》的重写版。

重写版从论文复现会重复处理相似问题切入，接着说明外部 Skill 如何改变执行，再逐节展开：

- SkillOpt 的 rollout、编辑预算和选择集门槛。
- WikiSkill 的轨迹、知识与技能分层，以及回滚时保留哪些内容。
- SkillForge 的领域创建、失败分析、缺陷定位与修订。

引用统计移到文末，机制成为正文主体。这个反馈不意味着以后固定写三篇论文、固定讨论自进化，也不意味着删除所有实验边界。

## 改写对照

### 从评价转到更新机制

容易写成材料评审：

> 我更关心的是它有没有形成可信的闭环。生成一份 Skill 不能证明系统真正学到了东西。

更接近目标文风：

> 候选 Skill 生成后，执行器在同一批选择任务上比较新旧版本。分数提高才采用修改；没有提高则继续使用旧版本，并把本次编辑和评分变化留给下一轮分析。

后一句说明系统怎样做，让评价有具体落点。只有材料确实具备这套机制时才能这样写。

### 从组件清单转到执行关系

过于抽象：

> 平台具备持久化、技能管理和可观测性，能够支持复杂长程任务。

更接近目标文风：

> 下一轮消息到达时，运行时先恢复上次的状态快照，再装配当前阶段需要的工具。执行中产生的消息和工具事件持续写入存储，轮次结束后保存新的快照。

顺序、读写对象与时机，使读者能够复述系统的运行过程。不要将这个示例当作任意平台的实现事实。
